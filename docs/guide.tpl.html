HAP Attachment Backup

HAP's app backup saves apps, worksheets, workflows, views and records, but not the files attached to records. This tool backs up those files on the client's Linux server that runs HAP, and names each one so HAP's Import Attachments can put it back on its record. Every run is logged, and built-in checks make problems easy to find.

At a glance

File name
<record title>_<original name>.<ext>
What is backed up
Every file in worksheet attachment fields, any type, from records that are not in the recycle bin.
When
Sunday 02:00 full copy. Monday to Saturday 02:00 new files only. Any time by hand.
Where
/data/hap-attachment-backup, or any folder set in backup.conf.
Kept for
The last 4 good full copies and 14 days of nightly runs. Older ones are removed automatically.
Logs
/var/log/hap-attachment-backup.log, plus a run.log in every backup set. --debug for full detail.
Effect on HAP
Reads only. The optional storage restore writes only files that are missing.
Install
One command from GitHub. Python 3 standard library only; nothing is added to the HAP containers.

Not included: discussion and chat files, logos, avatars and system icons. Only files attached to records are backed up.

How it works

  1. List attachmentsA read-only query in the HAP MongoDB container lists every attachment, its record title, app and worksheet.
  2. Copy filesEach file is streamed out of HAP storage with mc cat in the HAP app container.
  3. Name and checkFiles are named for Import Attachments and checksummed (SHA-256) into manifest.csv.
  4. Finish the setThe set is renamed from .partial only when complete, the result goes to last_run.json, and old sets are removed.
backup folder layout
/data/hap-attachment-backup/
  state.json                      # files already backed up (used by nightly runs)
  last_run.json                   # result of the last backup run
  full-2026-11-15_0200/           # Sunday full copy
    <App>/<Worksheet>/<Title>_<Original name>.<ext>
    manifest.csv                  # every file: record ID, title, original name, storage path, SHA-256
    missing.csv                   # attachments that could not be backed up, with the reason
    summary.txt                   # counts, versions, exit code
    run.log                       # log of the run that wrote this set
  incr-2026-11-16_0200/           # nightly: only files not backed up before
  incr-2026-11-17_0200/

To restore everything as of a given night, use the latest full set before that night plus every nightly set after it.

Install

On the client's HAP server, as root. The installer downloads the latest release, installs it, sets up the schedule and log rotation, and runs the system check.

curl -fsSL https://raw.githubusercontent.com/ChaiBoonHong/hap-attachment-backup/main/get.sh | sudo bash

Options

Add them after bash -s --:

G=https://raw.githubusercontent.com/ChaiBoonHong/hap-attachment-backup/main/get.sh
curl -fsSL $G | sudo bash -s -- --version v1.1.0   # a given release
curl -fsSL $G | sudo bash -s -- --no-cron          # no schedule
curl -fsSL $G | sudo bash -s -- /srv/hap-backup    # another install folder

Server without internet

Download the release file on a PC, copy it over, then on the server:

scp hap-attachment-backup-@@VERSION@@.tar.gz <user>@<server>:/tmp/
# on the server
cd /tmp && tar xzf hap-attachment-backup-@@VERSION@@.tar.gz
sudo bash hap-attachment-backup-@@VERSION@@/install.sh

Confirm the schedule

cat /etc/cron.d/hap-attachment-backup
timedatectl | grep 'Time zone'
/etc/cron.d/hap-attachment-backup
# Sunday 02:00 - full copy
0 2 * * 0   root /opt/hap-attachment-backup/hap-attachment-backup.sh --full --quiet >/dev/null 2>&1
# Monday-Saturday 02:00 - new files only
0 2 * * 1-6 root /opt/hap-attachment-backup/hap-attachment-backup.sh --incremental --quiet >/dev/null 2>&1

Times follow the server's time zone. To change the time, edit the file: the first two fields are minute and hour, so 30 3 * * 0 is Sunday 03:30. The morning after, sudo hap-attachment-backup --log shows how the night went.

Hand over

Before leaving a client server, confirm each of these:

  • --check shows 0 failed.
  • A full set exists and --verify reports all files OK.
  • missing.csv has been reviewed with the client; attachments with no file in HAP cannot be backed up.
  • The client knows where backups are kept, and has a plan to copy them off the server (see Day-to-day).
  • One Import Attachments restore was tried in a test worksheet (see Restore files).
  • The next morning, --log shows the 02:00 run finished with exit 0.

Debug mode

LOG_LEVEL=INFO logs each step, progress every 500 files or 60 seconds, warnings and errors. Debug also logs every Docker command with its exit code, time and error output, the settings in use (passwords hidden), counts per app, worksheet and field, and every file with its size, time and checksum. Use --debug for one run; leaving LOG_LEVEL=DEBUG on makes the log grow with every file.

sudo hap-attachment-backup --dry-run --debug   # how attachments are found, without copying
sudo hap-attachment-backup --check --debug     # every command the check runs
sudo hap-attachment-backup --log               # the last nightly run
sudo grep -E '\[(ERROR|WARNING)\]' /var/log/hap-attachment-backup.log | tail -20

Support bundle

When something needs a closer look, ask the client to run this and send the file it prints:

sudo hap-attachment-backup --support-bundle

The .tar.gz (in /tmp, readable by root only) holds the check result, status, settings with passwords hidden, the last 5000 log lines, the logs of the last three sets, and system details: OS, Docker, disk, containers, time zone. It holds no attachment files, but log lines can include app, worksheet and record names.

Safety checks built in

  • A second backup cannot start while one runs (exit code 3); the log names the running process.
  • A run stops with an error when the first 10 files cannot be read, instead of writing an empty set.
  • Sets are written to a hidden .<set>.partial folder and renamed only when complete. Unfinished folders stay for a day for inspection, then are removed.
  • Full sets where most files failed don't count toward KEEP_FULL, so failed nights never push good full copies out.
  • Files HAP lists but storage lacks are reported as file not in HAP storage in missing.csv, not as failures.

Restore files

Pick the method that matches what was lost.

Records exist, files are missing

A. Import Attachments in HAP

Use this after restoring an app from a HAP backup, or to put files back on records.

  1. Copy the worksheet folder to a PC (commands below). Use the latest full set, plus later nightly sets for the newest files.
  2. In HAP, open the worksheet, then Import › Import Attachments.
  3. Upload the files from <App>/<Worksheet>/. Up to 100 files and 2 GB per upload.
  4. File Name Matching Field: the worksheet's title field. Delimiter: _.
  5. Target field: the attachment field, shown in the field column of manifest.csv.
  6. Write mode: Append keeps existing files. Overwrite replaces them and cannot be undone.
Records intact, storage lost

B. Put files back into storage

Puts each file back at its original storage path, so records show their files again with the original file IDs. Files that already exist are left untouched.

sudo hap-attachment-backup --restore-storage full-2026-11-15_0200 --dry-run
sudo hap-attachment-backup --restore-storage full-2026-11-15_0200

Run it for the full set, then for each later nightly set.

Titles must be unique. Import Attachments matches on the text before the first _. If two records share a title, or a title contains _, files can land on the wrong record. manifest.csv keeps each file's record_id, and its note column flags these cases.

Copy one worksheet folder from the server to a PC:

# on the server
cd /data/hap-attachment-backup/full-2026-11-15_0200
sudo tar czf /tmp/restore.tgz "Sales CRM/Contracts"
sudo chmod 644 /tmp/restore.tgz

# on the PC (PowerShell or a terminal)
scp <user>@<server>:/tmp/restore.tgz .
tar -xzf restore.tgz

# back on the server, when done
sudo rm /tmp/restore.tgz

Day-to-day

CommandWhat it does
hap-attachment-backup --checkTests the whole setup; a fix for every problem
hap-attachment-backup --statusBackup sets with counts and sizes, last run, running now, schedule
hap-attachment-backup --log [N]The last backup run, or the last N log lines
hap-attachment-backup --dry-runWhat would be copied and what is missing. Writes nothing.

hap-attachment-backupCopies only new files into an incr-… set (same as --incremental). Writes no set when nothing is new.

Run them as root with sudo. Add --debug for full detail or --quiet to print only warnings and errors.

Exit codes

CodeMeaning
0Finished. Attachments with no file in HAP are listed in missing.csv but don't count as a failure.
1Error: settings, Docker, MongoDB, or storage unreadable. The log says which.
2Some files could not be copied, or failed verification
3Another backup or restore is still running
4Not enough disk space

Regular checks

  • Weekly: sudo hap-attachment-backup --status; the last run should be OK and less than a day old. Monitoring tools can read last_run.json instead.
  • After a HAP upgrade: --check and --dry-run, and compare the file counts. An upgrade can change how attachments are stored.
  • Monthly: --verify on the newest full set, and one Import Attachments restore in a test worksheet.

Keep a copy off the server

The default backup folder is on the server's own disk, so it does not protect against losing that disk. Copy it elsewhere on a schedule, for example:

sudo rsync -a /data/hap-attachment-backup/ backup-user@other-host:/backups/hap-attachments/
